## Blockers and Gaps

### D1 (WL-120)

- The `server/` subdirectory is not a Python package. The `_load_server_module_shared`
  helper loads submodules by file path — the new `tools_dynamic_registry.py` uses the
  same pattern and is registered in `server.py` the same way as all other extracted modules.
- Next extraction slice from Wave-1 plan: `server_resources_registry.py` (remaining
  `resource_*` wrapper glue).

### D2 (WL-136)

- Several of the 5 extracted commands already have canonical definitions in
  split-out modules. `cli_tooling.py` adds a single, annotated canonical home
  specifically for the WL-136 surface boundary.
- The old definitions in `cli.py` remain and are not deleted in this slice; that
  cleanup is the next WL-136 step (once callers are verified via import graph audit).

### D3 (WL-131)

- Rust parity tests are skip-guarded on `thegent_parser` import. The PyO3 extension
  must be built separately with `maturin develop` or `cargo build --lib`. The Rust-side
  unit tests in `crates/thegent-parser/src/lib.rs` cover the same cases.

### D4 (WL-132)

- `continue-on-error: true` means the zig-readiness gate is informational only.
  To make it blocking, change to `continue-on-error: false` when Zig promotion
  reaches P0 status.
- The `crates/` directory layout places the interop crate one level down, so
  `working-directory: crates` is set on both cargo steps.

### D5 (WL-133)

- `build_provider_score_kernel_script()` and `math.mojo` still have different
  weight formulas (Python: 0.4/0.35/0.25 vs Mojo: 0.5/0.3/0.2). The fixture is
  calibrated to the Python bridge formula. Before Mojo kernel promotion, these
  must be unified and the fixture updated. This gap was documented in Wave-1 D5.
- The async dispatch test requires `pytest-asyncio` and a live Mojo installation.
